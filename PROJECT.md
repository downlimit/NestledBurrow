# NestledBurrow: bootstrap проекта

## Назначение

`PROJECT.md` — короткий маршрутизатор контекста. Он не хранит историю задач, подробное состояние каждой механики или инструкции исполнителя.

Репозиторий: `downlimit/NestledBurrow`.
Runtime: Phaser 4, Vite, browser 2D, logical viewport `320×180`.

## Роли

- **Пользователь** владеет продуктовым, художественным и балансным решением.
- **Лид** обсуждает игру, выбирает границу задачи и готовит компактное ТЗ.
- **Codex** реализует одну задачу end-to-end.
- **Интегратор** по прямой просьбе принимает или чинит открытые PR.

Новый чат всегда читает `PROJECT.md`. После фразы `ты лид` читает `LEAD.md`; после `ты интегратор` — `REVIEW.md`.

## Режимы запроса Лиду

### Обсуждение или ТЗ

Лид читает только:

1. `PROJECT.md` и `LEAD.md`;
2. актуальный `main`, открытые PR и текущую секцию `ROADMAP.md`;
3. `LIBRARY.md`, чтобы выбрать один-два релевантных system-документа;
4. владельцев и потребителей затронутого кода.

`GAME.md` открывается для продуктового направления, а не перед каждой локальной задачей. Весь репозиторий, все system-документы и полная история задач заранее не читаются.

### Прямая реализация чатом

Запросы вроде `исправь`, `добавь в игру`, `замени ассет`, `обнови контент` без просьбы написать ТЗ означают, что чат выполняет изменение сам.

Перед кодом или контентом Лид дополнительно читает актуальный `AGENTS.md` и следует тому же исполнительному маршруту, что Codex: targeted context, preview для видимого результата, пользовательское `принято`, один Ready PR, final-head CI и merge. Роль чата остаётся Лидом; меняется только режим работы.

Draft PR до приёмки не является нормальным маршрутом. Он допустим только по прямой просьбе пользователя и должен быть явно назван исключением.

## Канонические владельцы

- `GAME.md` — цель игры, желаемый опыт и продуктовые принципы.
- `ROADMAP.md` — только активная работа, ближайшее направление и следующий Task number.
- `LIBRARY.md` — маршрутизация к system-документам и владельцам кода.
- `systems/*.md` — устойчивые контракты отдельных игровых систем.
- `ARCHITECTURE.md` — межсистемные границы и архитектурные ограничения.
- `LEAD.md` / `REVIEW.md` — ролевые маршруты.
- `AGENTS.md` — обязательный исполнительный контракт.
- `ASSETS.md` / `BINARY_IMPORT.md` — provenance и доставка бинарников.
- `FAST_LOOP.md` — человеческая ретроспектива скорости; не контекст обычной реализации.
- `tasks/*.md` — только большие возобновляемые контракты; старые файлы являются историей.

Один изменяемый факт имеет одного владельца. Документы не копируют друг у друга статусы, числа и полные описания систем.

## Продукт в одном абзаце

NestledBurrow — уютная игра о восстановлении таверны на летающем острове. Игрок добывает и выращивает ресурсы, готовит, обслуживает гостей, строит пространство, постепенно автоматизирует процессы и собирает вокруг себя живое поселение.

Подробный продуктовый контекст находится в `GAME.md`. Фактические системные контракты — в `systems/*.md`.

## Основной цикл разработки

```text
замысел
→ Task number и компактное ТЗ
→ одна ветка
→ managed preview и feedback для видимого результата
→ пользовательское `принято`
→ минимальная публикация
→ один Ready PR
→ final-head GitHub CI
→ один repair только при реальном failure
→ merge
```

Пользовательские комментарии и время тестирования не считаются потерями. Оптимизируются лишнее чтение, повторные доказательства, бессмысленные CI-циклы и работа агента, не влияющая на качество.

## Актуализация памяти

Если принятая задача меняет устойчивый контракт системы, исполнитель обновляет соответствующий `systems/*.md` в том же PR. `GAME.md` меняется только при продуктовом решении, `ARCHITECTURE.md` — только при межсистемной границе, `ROADMAP.md` — только при смене активной работы или номера.

После merge не создаётся отдельный документационный PR только ради записи SHA или пересказа уже завершённой задачи.
