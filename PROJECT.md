# NestledBurrow: bootstrap проекта

## Назначение

`PROJECT.md` — короткий маршрутизатор контекста. Он не хранит историю задач, подробное состояние каждой механики или инструкции исполнителя.

Репозиторий: `downlimit/NestledBurrow`.
Runtime: Phaser 4, Vite, browser 2D, logical viewport `640×360` with a `2×` world camera.

## Роли

- **Пользователь** владеет продуктовым, художественным и балансным решением.
- **Лид** обсуждает игру, выбирает границу задачи и готовит компактное ТЗ.
- **Художник** подготавливает approved visual assets, проверяет native grid, naming, placement и provenance.
- **Codex** реализует одну задачу end-to-end, используя только уже committed visual binaries.
- **Интегратор** по прямой просьбе принимает или чинит открытые PR.

Новый чат всегда читает `PROJECT.md`. После фразы `ты лид` читает `LEAD.md`; после `ты художник` — `ARTIST.md`; после `ты интегратор` — `REVIEW.md`.

Роль сохраняется на весь чат. Переключение роли выполняется только по явной просьбе пользователя.

## Режимы запроса Лиду

### Обсуждение или ТЗ

Лид читает только:

1. `PROJECT.md` и `LEAD.md`;
2. актуальный `main`, открытые PR и текущую секцию `ROADMAP.md`;
3. `LIBRARY.md`, чтобы выбрать один-два релевантных system-документа;
4. владельцев и потребителей затронутого кода;
5. перед техническим handoff — раздел `Архитектурные точки давления` в `ARCHITECTURE.md` для фактически затронутых owners.

`GAME.md` открывается для продуктового направления, а не перед каждой локальной задачей. Весь репозиторий, все system-документы и полная история задач заранее не читаются.

### Прямая реализация чатом

Запросы вроде `исправь`, `добавь в игру`, `замени ассет`, `обнови контент` без просьбы написать ТЗ означают, что чат выполняет изменение сам.

Перед кодом или контентом Лид дополнительно читает актуальный `AGENTS.md`. Для ChatGPT direct implementation видимый результат проходит прямой публичный Draft PR preview до пользовательского `принято`, затем тот же PR становится Ready, проходит final-head CI и merge. Codex использует локальный managed preview и создаёт Ready PR только после `принято`. Роль чата остаётся Лидом; меняется только режим работы.

Новый visual binary не изготавливается Codex. В Lead-чате художественная подготовка выполняется только после явного переключения в роль Художника либо через отдельный Artist-чат; затем Лид продолжает code-only integration route.

Draft PR до приёмки принадлежит только ChatGPT direct implementation и допустим по прямой просьбе пользователя. Команда `препроверка принята` разрешает task-ветку и Draft PR только как носитель реальной игровой сборки; публикацию Ready PR и merge разрешает только последующее `принято`. Codex до `принято` остаётся на локальном managed preview.

## Архитектурный gate задачи

Каждое техническое ТЗ и каждая прямая реализация объявляют одну строку Integration metadata:

```text
Architecture pressure: none
```

или:

```text
Architecture pressure: <owner> — <сработавший триггер и локальное выделение в этом PR>
```

`none` допустимо только после проверки затронутых owners по `ARCHITECTURE.md`. Если триггер сработал, выделение входит в ту же задачу, system contract и targeted acceptance; отдельный неопределённый cleanup follow-up не создаётся. При этом триггер не разрешает расширять scope на незатронутые части архитектуры.

## Канонические владельцы

- `GAME.md` — игровая фантазия, цель, желаемый опыт и продуктовые принципы; важный вижн не выбрасывается ради краткости, а подробности конкретных систем выносятся к их владельцам.
- `ROADMAP.md` — только активная работа, ближайшее направление и следующий Task number.
- `LIBRARY.md` — краткая карта существующих систем: что за что отвечает, какой `systems/*.md` читать и где находятся основные владельцы кода и проверки.
- `systems/*.md` — подробные устойчивые контракты отдельных игровых систем и их текущий фактический baseline.
- `ARCHITECTURE.md` — межсистемные границы, архитектурные ограничения и условные точки давления.
- `LEAD.md` / `ARTIST.md` / `REVIEW.md` — ролевые маршруты.
- `AGENTS.md` — обязательный исполнительный контракт.
- `ASSETS.md` / `BINARY_IMPORT.md` — provenance и доставка бинарников.
- `FAST_LOOP.md` — человеческая ретроспектива скорости; не контекст обычной реализации.
- `tasks/*.md` — только большие возобновляемые контракты; старые файлы являются историей.

Один изменяемый факт имеет одного владельца. Документы не копируют друг у друга статусы, числа и полные описания систем.

## Продукт в одном абзаце

NestledBurrow — уютная игра о восстановлении таверны на летающем острове. Игрок добывает и выращивает ресурсы, готовит, обслуживает гостей, строит пространство, постепенно автоматизирует процессы и собирает вокруг себя живое поселение.

Подробный продуктовый контекст находится в `GAME.md`. Фактические системные контракты — в `systems/*.md`.

## Основной цикл разработки

```text
замысел
→ при необходимости approved visual binary от Художника
→ architecture pressure declaration
→ Task number и компактное ТЗ
→ одна ветка
→ прямой публичный PR preview и feedback для видимого результата
→ пользовательское `принято`
→ минимальная публикация
→ один Ready PR
→ final-head GitHub CI
→ один repair только при реальном failure
→ merge
```

Пользовательские комментарии и время тестирования не считаются потерями. Оптимизируются лишнее чтение, повторные доказательства, бессмысленные CI-циклы и работа агента, не влияющая на качество.

## Зелёный `main`

Любое изменение репозитория, включая документацию и процесс, проходит через ветку и PR; прямые записи в `main` не являются рабочим маршрутом. Невидимая micro-правка получает короткий Ready PR без preview и без участия пользователя: агент сам проводит проверку и merge. Push-проверка `main` служит только аварийной сеткой, а не заменой PR.

## Актуализация памяти

Если принятая задача меняет устойчивый контракт системы, исполнитель обновляет соответствующий `systems/*.md` в том же PR. `GAME.md` меняется только при продуктовом решении, `ARCHITECTURE.md` — только при межсистемной границе или принятой точке давления, `ROADMAP.md` — только при смене активной работы или номера.

После merge не создаётся отдельный документационный PR только ради записи SHA или пересказа уже завершённой задачи.
