# NestledBurrow: roadmap и текущее исполнение

## Назначение

`ROADMAP.md` отвечает:

1. что делается сейчас;
2. что проверяется следующим.

Состояние механик и пользовательский verdict принадлежат `GAME.md`. Код, checks и merged PR доказывают техническую реализацию.

## Идентификаторы

Каждая согласованная работа получает постоянный номер до Codex prompt:

```text
Task #001 — Первая расчистка участка
```

После открытия PR используется Task-first адрес:

```text
Task #001 — Первая расчистка участка (PR #81)
```

- номера последовательны и не переиспользуются;
- один пользовательский результат сохраняет identity от prompt до merge;
- branch: `task/<номер>-<slug>`;
- Base SHA Лид проверяет непосредственно перед запуском.

**Следующий свободный номер:** `Task #037`.

## Статусы

- `Запланировано` — направление согласовано;
- `Готово к запуску` — prompt подготовлен;
- `В работе` — Codex выполняет задачу;
- `PR открыт` — идёт CI/review;
- `Смёржено, ждёт теста` — код в `main`, verdict ещё нет;
- `Принято` / `Переделать` / `Отклонено` — решение пользователя;
- `Завершено` — техническая/process работа завершена;
- `Заблокировано` — указан конкретный blocker.

## Сейчас

### Task #036 — Ускорить публикацию и стабилизировать Windows-инструменты

**Статус:** `Завершено` после merge этой ветки.

**Наблюдаемый результат:** пользовательские feedback-итерации явно считаются продуктовой работой и не ограничиваются. После `принято` Fast-задача за несколько минут активной работы доходит до Ready PR: принятый healthy preview не дублируется локальным full check/build/E2E без конкретного риска, а полный contract остаётся PR CI. Python checks используют portable launcher; preview и focused-E2E outputs живут в OS temp; worktree не смешивает уровни прав. Ретроспектива #030–#035 и актуальная архитектурная память закреплены в канонических документах.

**Граница:** без ослабления final-head CI, удаления Browser E2E, ограничения пользовательского feedback, изменения gameplay, dependencies или общего rewrite `WorldScene`.

### Task #035 — Исправить мобильное меню строительства и джойстик

**Статус:** `Заблокировано` публикацией.

**Фактическое состояние:** пользователь принял локальный preview в исходной Codex-сессии, и там создан локальный commit, но ветка/PR отсутствуют на GitHub. Для завершения исходный Codex должен опубликовать существующую работу, пройти final-head CI и merge; повторная реализация с нуля не назначается.

**Продуктовый вопрос:** становится ли режим строительства на смартфоне читаемым и естественным для touch, а джойстик — предсказуемым у любого края экрана?

**Наблюдаемый результат:** RU/EN-тексты library корректны в `320×180` и coarse-pointer viewport; library прокручивается finger drag с инерцией без ложного выбора/строительства; tap выбирает asset. Центр джойстика совпадает с touch даже у края, sprint-ring может выходить за viewport, а его alpha уменьшена вдвое без изменения радиуса, threshold и movement math.

**Граница:** без новых assets/dependencies, переработки catalog, вращения/сохранения построек, изменения `sprintRadius`, `maxOffset`, dead zone, speed, energy, camera, world bounds или desktop build UX.

### Task #034 — Заменить мебель и добавить случайный музыкальный плейлист

**Статус:** `Принято`.

Canonical shower/toilet/table PNG используют native footprint; bed и build previews также используют canonical furniture sprites. Семь MP3 воспроизводятся случайно без immediate repeat, с fade/overlap. Facility/sleep сохраняют motor position, camera следует presentation position.

### Task #033 — Исправить сетку таверны и добавить режим строительства

**Статус:** `Принято`.

16 px world cells и edge-walls используют общую render/collision geometry. Build library поддерживает стены, surfaces, furniture/tree, drag prediction, demolition, sprite highlight, grouped `Ctrl+Z` и доступный WASD. Постройки runtime-only.

### Task #032 — Увеличить внешний sprint-ring мобильного джойстика

**Статус:** `Принято`.

Радиус и sprint threshold внешней окружности — `54.45 px`; остальные input/movement contracts не менялись.

Mobile sprint, held repeatable resource actions, coarse-pointer tooltips, facility presentation pose, camera B/F/C и debug tuning интегрированы.

## Следующее продуктовое направление

После завершения Task #036 и публикации Task #035 приоритет возвращается gameplay/content. Следующие 4–5 задач не меняют процесс без повторившегося дорогого blocker.

Ближайший продуктовый критерий из `GAME.md`: игрок самостоятельно формулирует небольшой план на следующий игровой день и реализует его через связанные системы участка, потребностей и простого сервиса таверны.
