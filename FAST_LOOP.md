# Task #020 — Ускорить цикл Codex

Этот файл хранит человеческий аудит скорости. Исполняемые правила находятся в `AGENTS.md`; Codex не перечитывает этот документ перед обычной задачей.

## Что оптимизируется

Цель — уменьшать активное время и расход лимитов на действия агента, которые не добавляют качества.

Не считаются процессными потерями:

- пользовательские feedback-итерации;
- время пользовательского теста preview;
- творческий подбор ощущения, баланса и визуала;
- рост задачи по прямым комментариям пользователя, если работа остаётся связным результатом.

Отдельно измеряются:

1. active implementation;
2. preview feedback;
3. active publication после `принято`;
4. remote CI waiting;
5. repair и cleanup.

## Исторический аудит Task #018

Task #018 заняла около 34 минут, израсходовала больше 20% недельного лимита и изменила 21 файл. Главные излишки: prompt на 438 строк, повторные build/check/E2E, шесть screenshot-состояний, Draft как CI-gate, лишний worktree/npm ci, загрузка полных успешных логов и отдельный Integrator handoff.

Результатом Task #020 стали компактные briefs, один локальный путь, один удалённый CI, Ready PR без Draft-gate, автоматическое завершение обычной задачи и сокращение постоянного процессного контекста примерно на 58%.

## Приоритетный чеклист

### P0 — действует всегда

- [x] Пользователь → Лид → компактное ТЗ → Codex end-to-end.
- [x] Integrator только по прямому запросу или для зависимой очереди PR.
- [x] Routine prompt не повторяет `AGENTS.md`.
- [x] Один сильный proof на material risk.
- [x] Один Ready PR; repair остаётся в той же ветке.
- [x] После зелёного CI обычная задача заканчивается merge и актуальным `main`.
- [x] Пользователь не обслуживает ветки, PR, CI или merge.
- [x] Feedback пользователя не ограничивается и не оценивается как waste.

### P1 — player-visible и runtime

- [x] Один managed preview URL живёт до `принято`.
- [x] Publication-проверки не выполняются после каждого feedback-пакета.
- [x] Успешный proof сохраняет силу, пока не изменились его входы.
- [x] Полный Browser E2E принадлежит PR CI.
- [x] Focused local E2E запускается только для скрытого риска, который нельзя доказать preview или более дешёвым contract check.
- [x] После `принято` Fast-задача не повторяет локально full check/build/E2E «на всякий случай».
- [x] Перед CI repair ожидаются terminal jobs одного SHA; failures объединяются одним пакетом.
- [x] Успешные логи остаются короткими; полные данные загружаются только при failure.

### P2 — среда и деградация

- [x] Python-checks не зависят от ручного поиска `python.exe`.
- [x] Preview/E2E operational files не пишутся в проблемные repository paths.
- [x] Worktree создаётся и используется под одним уровнем прав.
- [x] Durable `tasks/*.md` остаются только для возобновляемой или зависимой работы.
- [x] Сравнить игровые задачи #030–#035 по внутренним ретроспективам.
- [ ] После следующих 4–5 gameplay-задач проверить только повторившиеся дорогие bottlenecks.

## Целевой быстрый цикл

```text
свободное описание пользователя
→ компактное архитектурно осмысленное ТЗ
→ реализация
→ managed preview
→ любое нужное число feedback-итераций
→ пользовательское `принято`
→ минимальная Fast-публикация или один Strict gate
→ Ready PR с auto-merge
→ полный GitHub CI
→ один repair только при реальном failure
→ merge и актуальный main
```

Feedback-фаза не имеет искусственного лимита времени. После `принято` ориентир Fast-задачи — попасть в Ready PR за несколько минут активной работы; ожидание GitHub CI считается отдельно. Strict-задачи могут занимать дольше только из-за конкретного риска, а не размера diff.

## Ретроспектива Task #025

Task #025 показала: промежуточные publication checks обесценивались следующим feedback, repair был отправлен до завершения всех jobs, consumer sweep не охватил изменённые ожидания, локальный общий E2E конфликтовал с preview, а частый polling расходовал контекст. Task #029 разделила feedback-gate и publication-gate, ввела managed preview, terminal repair и failure-only artifacts.

## Ретроспектива Task #030–#035

Исполнители пяти игровых задач отдельно проанализировали свои сессии.

### Что не является проблемой

- Task #030 получила семь содержательных feedback-пакетов.
- Task #033 выросла в полноценный редактор и получила десятки визуальных замечаний.
- Task #034 получила несколько итераций по позиции и камере.

Эти циклы улучшили игру и не должны сокращаться ради формальной скорости.

### Подтверждённые потери

1. **Долгая активная публикация после `принято`.** Агенты повторяли full check, build и иногда local E2E, хотя пользователь уже подтвердил здоровый preview, а PR CI всё равно выполнял полный контракт.
2. **Windows/Python/permissions.** В большинстве задач повторялись отсутствие `python` в PATH, ручной bundled-runtime fallback, `EPERM`, разные уровни прав и cleanup временных outputs.
3. **Focused E2E использовался шире названия.** Иногда он запускал десятки tests и оставлял writable artifacts в worktree.
4. **`src/main.js` концентрирует orchestration.** Это особенно замедляло build mode и facility/camera изменения, но оправдывает только use-case-driven extraction, а не отдельный общий rewrite.

### Что сработало

- Preview стабильно находил UX/visual дефекты, недоступные статическим checks.
- Task #033, несмотря на большой product scope, прошла один финальный CI с первой попытки примерно за две минуты.
- CI repairs #030/#031/#034 поймали реальные или устаревшие browser expectations и остались в тех же PR.
- Маленькая Task #032 прошла быстрым параметрическим циклом без лишней архитектуры.

### Решения Task #036

- Fast publication после `принято` использует принятый preview и только ещё не доказанные targeted risks.
- Полный локальный `npm run check`, standalone build и focused E2E не являются default для Fast-задачи; полный repository contract остаётся в PR CI.
- Python-checks используют portable launcher.
- Preview и focused-E2E state/artifacts перемещены в OS temp.
- Worktree не смешивает elevated и normal operations.
- Архитектурные сигналы build-mode и facility/camera закреплены в `ARCHITECTURE.md` и `LEAD.md`.

## Когда снова менять процесс

Следующая process-задача допускается только когда:

- один дорогой hidden-action bottleneck повторился минимум дважды;
- active publication Fast-задачи снова регулярно превышает несколько минут до Ready PR;
- среда требует ручного вмешательства пользователя;
- существует риск повреждения `main`, save или пользовательских assets.

До этого приоритет — gameplay/content задачи.
