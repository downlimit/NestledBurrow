# Lead protocol for NestledBurrow

## Роль

Лид переводит свободное описание пользователя в небольшой наблюдаемый результат. Пользователь не обязан знать архитектуру, GitHub или названия файлов.

Лид не загружает весь проект «на всякий случай». Глубина исследования определяется затронутой системой, а не размером игры.

## Сначала определить режим

### 1. Обсуждение

Для геймдизайна, архитектуры, выбора направления и оценки идей не создаётся Task и не меняется репозиторий, пока пользователь не подтвердил устойчивое решение.

### 2. Подготовка ТЗ

Фразы `напиши ТЗ`, `дай промпт Codex`, `подготовь задачу` означают Lead handoff. Лид выдаёт один copy-paste блок и не реализует задачу сам.

### 3. Прямая реализация

Фразы `исправь`, `добавь`, `замени`, `обнови в игре/репозитории` без просьбы о ТЗ означают direct implementation. Перед изменением Лид читает `AGENTS.md` и выполняет его маршрут самостоятельно. Нельзя отвечать планом вместо доступного действия.

### 4. Препроверка чат-демонстрации

Это правило относится только к прямой реализации через ChatGPT и не меняет маршрут Codex.

Лид может сначала выдать отдельную HTML-демонстрацию поведения, не интегрированную в игру. Такая демонстрация всегда называется макетом, а не реализацией или project preview.

Фразы пользователя `препроверка ок` или `препроверка принята` означают, что макет принят как направление. Лид обязан внедрить результат непосредственно в игру, а не выдавать следующий автономный preview системы.

Эта команда явно разрешает ChatGPT записывать реализацию в task-ветку и при необходимости открыть Draft PR только как носитель настоящего игрового preview. Она не разрешает Ready PR, auto-merge или merge.

Следующий результат для пользователя должен быть запущен из реального проекта и содержать систему внутри самой игры. Затем пользователь либо даёт правки, либо пишет `принято`. Только `принято` завершает preview acceptance и разрешает публикационный маршрут.

## Контекстный бюджет

Перед локальной задачей:

1. прочитать `PROJECT.md`, `LEAD.md`;
2. проверить актуальный `main`, открытые PR и только верхнюю активную часть `ROADMAP.md`;
3. открыть `LIBRARY.md`;
4. выбрать обычно один, максимум два system-документа;
5. изучить конкретных владельцев и потребителей затронутых контрактов;
6. расширять контекст только после найденной реальной зависимости.

Не читать автоматически весь `GAME.md`, всю историю `ROADMAP.md`, все `systems/*.md`, `FAST_LOOP.md`, старые `tasks/*.md` или весь репозиторий.

`GAME.md` нужен, когда меняется продуктовая цель или связь систем. `ARCHITECTURE.md` нужен при межсистемном изменении, новом owner или работе с `src/main.js`.

## Task identity

Согласованная работа получает следующий номер из `ROADMAP.md`:

```text
Task #001 — Первая расчистка участка
Task #001 — Первая расчистка участка (PR #81)
```

Номер сохраняется при feedback, repair и rebase. Ветка: `task/<number>-<slug>`.

## Компактное ТЗ

Обычное ТЗ содержит:

1. Task title;
2. цель и наблюдаемый результат;
3. релевантные system-документы;
4. только критические инварианты;
5. acceptance, который нельзя вывести из кода;
6. scope boundary только при реальном риске расширения.

Бюджет результата: `20–50` непустых строк для обычной задачи, `50–100` для migration, dependency, asset или нескольких тесно связанных систем. Это бюджет выдачи, а не необязательный ориентир.

Перед выдачей Лид обязан посчитать непустые строки и выполнить compression gate:

1. удалить внутренний анализ, историю исследования и рассмотренные альтернативы;
2. удалить всё, что Codex восстановит из `AGENTS.md`, названных system-документов, `LIBRARY.md` и кода владельцев/потребителей;
3. удалить предполагаемые шаги реализации, полный список файлов, обычные checks, Git lifecycle и каталоги возможных багов «на всякий случай»;
4. оставить строку только если её удаление может изменить наблюдаемый результат, нарушить подтверждённое решение пользователя, потерять невосстановимый контракт или сделать acceptance/scope неоднозначным.

Объём исследования никогда не оправдывает объём ТЗ. Исследование нужно Лиду для отбора нескольких ограничений, а не для передачи всего анализа Codex.

ТЗ длиннее `100` непустых строк считается некорректным и не выдаётся, кроме редкого `Size exception`. Лид может применить исключение на своё усмотрение только когда одновременно выполнены все условия:

- задача даёт один неделимый подтверждённый результат, который нельзя безопасно разбить на самостоятельные задачи;
- превышение вызвано точными migration, dependency, binary, external или cross-system compatibility контрактами, которые нельзя восстановить ссылкой на канонический файл;
- после compression gate каждая превышающая бюджет секция всё ещё необходима для корректного решения.

Сразу после Task title такое ТЗ обязано содержать строку `Size exception: <одна конкретная причина>; <N> непустых строк.` Причина должна объяснять, почему сокращение или разделение изменит результат, а не почему задача сложная.

Недопустимые причины исключения: «затронуто много систем», «задача важная/сложная», «хочу предусмотреть баги», «для самодостаточности», «так надёжнее», «проведено много исследования» или удобство Лида. Если причину нельзя сформулировать одним предложением либо результат можно разделить без потери смысла, ТЗ необходимо сократить или разбить.

Для ТЗ длиннее `150` строк объяснительная часть всё равно должна помещаться в `100` строк; превышение допускается только за счёт точных таблиц, manifest, mapping или compatibility matrix, которые невозможно заменить канонической ссылкой. `Size exception` снимает только числовой бюджет и никогда не разрешает гигантский объяснительный текст, implementation diary или проектирование за исполнителя.

Не копировать `AGENTS.md`, полный список файлов, историю системы, все существующие checks, Git lifecycle или объяснение всей игры.

ТЗ выдаётся одним непрерывным fenced-блоком `text`.

## Архитектурная дисциплина

`src/main.js` — composition root, а не место для новых state machines и domain logic. Перед задачей, которая добавляет build/authoring, guest/service, persistence или presentation orchestration, Лид проверяет `ARCHITECTURE.md`.

Если новая логика иначе увеличит `src/main.js`, ТЗ должно направить её в существующий runtime/coordinator либо включить небольшое use-case-driven выделение. Общий rewrite, ECS или event bus без доказанного use case запрещены.

## Документация в задаче

В ТЗ указывается только system-документ, устойчивый контракт которого реально меняется. Исполнитель обновляет его в том же PR.

- продуктовая цель → `GAME.md`;
- активная работа/номер → `ROADMAP.md`;
- локальный системный контракт → соответствующий `systems/*.md`;
- межсистемная граница → `ARCHITECTURE.md`;
- адреса владельцев → `LIBRARY.md`.

Не создавать отдельный documentation follow-up после merge.

## Preview и публикация

Player-visible gameplay, UI, input, localization, animation, audio и assets требуют `Preview acceptance: required`.

До `принято`: один прямой публичный PR preview URL, пакетные feedback-правки, только минимальное доказательство скрытого риска. Ссылка должна открывать уже собранную игру; StackBlitz, Codespaces и другие ссылки, которые сначала поднимают dev-среду, не являются пользовательским preview.

После `принято`: Fast-задача не повторяет full check/build/E2E без конкретной причины; выполняются diff review и только ещё не доказанные targeted risks, затем один Ready PR и final-head CI.

Draft PR до приёмки разрешён только прямой командой пользователя; команды препроверки из раздела 4 считаются такой прямой командой только для ChatGPT direct implementation.

## Visual assets

Codex никогда не генерирует, не дорисовывает, не интерпретирует, не заменяет и не подготавливает игровые изображения.

Любая просьба о новой графике автоматически проходит через Lead asset-preparation route:

1. Лид определяет полный список обязательных бинарников;
2. проверяет Basic Village и уже принятые project assets;
3. самостоятельно подготавливает отсутствующие изображения;
4. проверяет native pixel grid, frame order, transparency, palette, nearest-neighbor contract, provenance и лицензию;
5. доставляет immutable binaries в canonical paths;
6. фиксирует размеры, byte length, SHA-256 и manifest;
7. только после read-back готовых файлов выдаёт Codex code-only integration task по `BINARY_IMPORT.md`.

Для pixel art визуальная «пиксельность» не является доказательством native asset. Крупный raster с блочными формами, glow, blur, antialiasing, мягкими краями, фоном, подписями или нецелочисленным масштабом считается только concept/reference. Его запрещено уменьшать, нарезать или выдавать за runtime spritesheet.

Runtime pixel-art binary должен быть создан непосредственно на точной native frame grid либо состоять из точных пикселей уже принятого native-grid источника. До приёмки Лид декодирует PNG, проверяет реальные dimensions, RGBA/alpha, frame bounds и order, а пользователю показывает nearest-neighbor contact sheet, построенный именно из финального runtime binary. Contact sheet и сгенерированный концепт никогда не являются runtime-источником.

Явная просьба пользователя создать графику не является разрешением передать её генерацию Codex. Изменить это разделение ответственности можно только отдельным прямым решением пользователя о смене самого процесса.

Если обязательного бинарника ещё нет в подтверждённом Base SHA, задача заблокирована. Codex не получает placeholder, ожидаемый путь к отсутствующему файлу или разрешение изготовить замену.
