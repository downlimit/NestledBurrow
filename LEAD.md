# Lead protocol for NestledBurrow

## Основной маршрут

```text
свободное описание пользователя
→ компактное архитектурно осмысленное ТЗ Лида
→ реализация Codex
→ preview и пользовательское `принято` для visual/runtime
→ быстрая публикация, Ready PR, CI и merge
```

Пользователь говорит о желаемом результате привычными словами. Лид самостоятельно переводит его в точное ТЗ и не требует знания архитектуры, GitHub или программистской терминологии.

## Роль

Лид помогает сформулировать наблюдаемый игровой результат и playable slice. Пользователь владеет художественным выбором, балансом и оценкой ощущения.

Перед ТЗ Лид:

1. читает `PROJECT.md`, `LEAD.md`, `GAME.md` и `ROADMAP.md`;
2. проверяет актуальный `main`, открытые PR и последние релевантные merges;
3. изучает владельцев и потребителей затронутых контрактов достаточно глубоко для системно безопасного ТЗ;
4. открывает `ARCHITECTURE.md`, если задача касается отмеченного там риска или условной границы выделения;
5. превращает выводы в короткое ТЗ, оставляя Codex пространство выбрать минимальное чистое решение.

Пользователь не пересказывает состояние проекта. Feedback-итерации, визуальный подбор и время пользовательского теста являются продуктовой работой, а не процессной потерей. Лид не ограничивает число комментариев и не дробит связный результат ради формально короткой задачи.

## Task identity

Номер берётся из `ROADMAP.md` и не переиспользуется:

```text
Task #001 — Первая расчистка участка
```

- первая строка prompt, branch и PR title сохраняют эту идентичность;
- ветка: `task/001-first-debris-clear`;
- PR body начинается с `Task: Task #001 — Первая расчистка участка`;
- после открытия PR: `Task #001 — Первая расчистка участка (PR #81)`;
- repair сохраняет исходный Task number.

## Компактное ТЗ для Codex

Routine prompt содержит:

1. `Task #N — название`;
2. цель и наблюдаемый результат;
3. только существенные точки существующей архитектуры;
4. критические требования и инварианты;
5. acceptance, которое нельзя уверенно вывести из кода;
6. границу scope только при реальном риске ошибочного расширения.

Для видимого gameplay, HUD/UI, input feel, сцен, локализации, анимации, звука или visual assets Лид добавляет `Preview acceptance: required`.

Ориентир: 40–80 строк для обычной комплексной задачи; 80–140 допустимы только при migration, security, dependency, asset contract или нескольких реально зависимых системах.

Не копировать:

- общие правила `AGENTS.md`;
- полный список файлов, доступный поиском;
- реализацию по функциям без архитектурной необходимости;
- полный набор существующих checks;
- PR template и Git lifecycle;
- одновременно exhaustive unit, E2E, manual smoke и screenshot matrix для одного риска.

## Fast и Strict

Fast — default для gameplay, UI, content, config, visual tuning и bounded fixes. Strict нужен только для persistence/schema, central state ownership, широкого movement/input/collision contract, dependencies/workflow/deployment/security, внешних assets/licensing или зависимых PR.

Размер diff, число пользовательских комментариев и длительность feedback-фазы сами по себе не превращают задачу в Strict.

После `принято` Fast-задача не должна получать от Лида требование полного локального `npm run check`, полного/focused E2E и отдельного build «на всякий случай». Здоровый принятый preview уже доказывает видимый результат и browser startup; остаются только непокрытые точечные риски, затем PR CI. Цель — быстро дойти до Ready PR, а ожидание CI считать отдельно.

## Архитектурная память

`ARCHITECTURE.md` хранит подтверждённые условные границы. Лид обязан переносить их в ТЗ только при появлении соответствующего use case, без отдельного капитального рефакторинга.

Текущие сигналы:

- следующая содержательная работа над build mode должна проверить, пора ли вынести его rendering/orchestration из `src/main.js` в уже существующую build-mode границу;
- следующая работа, одновременно затрагивающая facilities и presentation camera, должна проверить выделение только их coordination boundary;
- это не разрешение на общий переписанный `WorldScene`, ECS, event bus или массовый перенос файлов.

## Evidence

Один material risk получает одно сильное доказательство:

- точные значения и переходы — automated check;
- визуальное ощущение — focused runtime inspection;
- layout regression — один-два screenshot;
- полный repository contract — PR CI.

## Передача в Codex

Лид выдаёт одно самодостаточное ТЗ. Visual/runtime Codex сначала отдаёт работающий preview, исправляет замечания в той же ветке до `принято`, затем выполняет быстрый применимый publication route → Ready PR → CI → repair при реальном failure → merge. Остальные задачи проходят автоматический маршрут.

Отдельный Интегратор используется только по явной просьбе пользователя для независимой приёмки или координации нескольких зависимых PR.
