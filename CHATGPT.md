# ChatGPT direct через GitHub connector

## Назначение

Этот маршрут используется обычным ChatGPT, когда он сам меняет `downlimit/NestledBurrow` через GitHub connector без локального worktree и shell. Codex продолжает работать по `AGENTS.md`; ChatGPT direct не читает `AGENTS.md`, если задача не меняет сам Codex-контракт.

Цель маршрута — сделать как можно меньше удалённых операций, не заменяя доказательства догадками и не используя GitHub Actions как интерактивный терминал.

## Контекст

До реализации уже прочитаны `PROJECT.md` и `LEAD.md`. Затем:

1. получить текущий SHA `main` один раз и считать его Base SHA;
2. через `LIBRARY.md` выбрать один, максимум два `systems/*.md`;
3. прочитать только затронутых owners, consumers и tests;
4. расширять контекст только по найденной зависимости.

Не перечитывать неизменившийся файл, SHA, PR или CI без причины. Не обходить весь репозиторий и не читать историю Task заранее. Для поиска сначала использовать канонические owners из `LIBRARY.md`; repository search нужен только когда реальная ссылка/consumer неизвестны.

## Один кандидат — одна публикация

До первой записи собрать связный candidate diff целиком. Ветка создаётся от Base SHA перед записью.

Multi-file изменение публикуется атомарно: один Git tree → один commit → одно перемещение task branch. `create_file` / `update_file` допустимы только для действительно одиночного файла. Не делать commit на каждый файл, status commit, пустой commit или отдельный commit только ради документации/SHA.

GitHub является владельцем текущего head SHA. Не переписывать PR body только для записи нового SHA и не дублировать туда изменяемый delivery status сверх обязательной metadata.

## Игровая препроверка

Player-visible задача открывает Draft PR только после первого связного playable candidate. Metadata: `executor: chatgpt`, `player-visible: yes`, `preview-acceptance: pending`. Draft нужен как носитель настоящей онлайн-сборки, а не как место для промежуточной разработки.

Feedback пользователя пакетируется: один раунд замечаний → один следующий связный commit. Во время feedback не менять PR body, если не меняется delivery metadata; `synchronize` сам обновит preview того же PR.

После `принято` сначала, пока PR ещё Draft, поставить `preview-acceptance: accepted`, затем удалить preview и перевести тот же PR в Ready. Accepted SHA сохраняется, если repair/rebase не нужен.

Невидимая задача не создаёт Draft/preview и не требует пользовательского gate: один финальный candidate → один Ready PR.

## Проверки и repair

До Ready не использовать GitHub Actions как цикл `edit → CI → edit`. Draft preview build подтверждает сборку видимого candidate; дополнительные удалённые доказательства нужны только для конкретного риска, который иначе нельзя проверить.

Ready PR является границей полного CI. После его запуска не редактировать body/title без смысловой причины. Если CI упал, дождаться terminal-состояния всех jobs этого head, собрать все содержательные failures одним пакетом и сделать один repair commit в той же ветке/PR. Same-head rerun допустим только при признаке инфраструктурного сбоя.

После зелёного final-head CI merge выполняется без дополнительного зеркального review/run.

## Устойчивые тесты

Регрессия защищает текущее поведение или контракт владельца, а не фотографию реализации Task. Не привязывать тест к форматированию source, внутренней форме вызова, чужой версии save schema или полному снимку живого global state, если это не сам проверяемый контракт.

Использовать канонические constants/helpers вместо скопированных чисел. Для времени, движения, ввода и другого меняющегося состояния либо заморозить несущественное изменение, либо проверять invariant относительно текущего состояния. Если новое законное поведение ломает старый тест, сначала определить актуальный контракт; runtime меняется только при настоящей регрессии.

## Границы

`src/main.js` остаётся composition root. Объявление `Architecture pressure` из Lead-маршрута обязательно; сработавшая точка давления исправляется локально в том же PR. Изменение устойчивого системного контракта обновляет его `systems/*.md` в том же commit/candidate.

В роли Лида ChatGPT не изготавливает новый игровой visual binary. Используются только уже утверждённые и committed assets; новая художественная подготовка принадлежит роли Художника.
